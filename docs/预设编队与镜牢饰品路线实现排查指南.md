# 预设编队与镜牢饰品路线实现排查指南

> 本文记录“小指良伪单通”预设编队、House of Spiders 饰品路线、5/15 层环境适配和队伍页面预设选择功能的实际实现方式。
>
> 对应实现提交：`7d440b62 feat: add extensible mirror team presets and routes`
>
> 需求与攻略方案见：[小指良伪单通-5/15 层饰品路线与编队方案](./小指良伪单通-5_15层饰品路线与编队方案.md)

## 1. 先看整体数据流

实现把“队伍预设”和“饰品路线”拆成两个目录。队伍预设只负责提供完整队伍模板和展示说明；队伍保存后，镜牢运行时只通过 `mirror_route_profile` 找到对应饰品路线。

```text
assets/config/config.example.yaml
        │
        └─ Config._merge_builtin_team_presets()
              按 team_presets_revision 合并缺失的内置默认队伍

module/team_presets.py
        │  BuiltinTeamPreset(presetId, routeId, 说明, 完整 TeamSetting)
        │
        └─ team.preset.list
              ▼
GPUI TeamsState.presets
        │
        ├─ 空槽：复制完整 TeamDetail，附加目标 teamNumber，立即 team.save
        └─ 已有队伍：先保存 target + preset，二次确认后保留 id/enabled 再 team.save
        │
        ▼
config.yaml 的 TeamSetting.mirror_route_profile
        │
        ▼
tasks/mirror/mirror.py
        ├─ get_mirror_route(route_id)
        ├─ MirrorPlanRuntime：按任务难度锁定本轮是 5 层还是 15 层，并跟踪五层段进度
        ├─ select_theme_pack：按楼层叠加主题包权重
        ├─ acquire_ego_gift：按路线优先选择奖励饰品
        └─ Shop：购买、路线配方合成、保护和升级路线饰品
```

对于没有设置 `mirror_route_profile` 的旧队伍，`get_mirror_route()` 返回默认路线，主题包、饰品、商店和合成继续走原有逻辑。

## 2. 预设编队目录

### 2.1 Python 目录是真实后端目录

文件：`module/team_presets.py`

核心类型是不可变的 `BuiltinTeamPreset`，字段分为三组：

- 标识：`preset_id`、`route_id`。
- 展示：中英文名称、说明、楼层提示、路线名称。
- 模板：完整的 `setting` 字典，最后通过 `TeamSetting.model_validate()` 校验。

当前内置目录有三项，其中小指良伪单通按普通/困难镜牢拆成两个模板：

| `preset_id` | `route_id` | 用途 |
| --- | --- | --- |
| `hos_ryoshu_solo_normal` | `hos_ryoshu_solo_route` | 小指良伪单通（普牢），默认前四个一级星光 |
| `hos_ryoshu_solo_hard` | `hos_ryoshu_solo_route` | 小指良伪单通（困牢），十个 ++ 星光 |
| `spiderweb_family` | `spiderweb_family_route` | 蜘蛛巢全家桶，保留原有专属 Gift Search |

`builtin_team_presets(team_detail)` 不直接拼接 GPUI 字段，而是把模板先交给后端已有的 `_team_detail()` 投影。因此预设和正常队伍的默认值、人格顺序、镜牢字段格式保持一致。

### 2.2 标识的职责

- `presetId` 只用于在预设目录中定位模板，不依赖中文显示名称。当前保存到用户队伍后不会持久化 `presetId`；两个小指良模板分别使用 `hos_ryoshu_solo_normal` 和 `hos_ryoshu_solo_hard`。
- `routeId` 是独立的饰品路线标识。保存时真正进入 `TeamSetting` 的字段是 `mirror_route_profile`。
- 两个小指良模板共用 `hos_ryoshu_solo_route`，显示名称分别为“`小指良伪单通（普牢）`”和“`小指良伪单通（困牢）`”。
- 用户保存预设后即使手动修改人格，仍会保留该队伍的 `mirror_route_profile`，因此仍会按该路线运行。若用户不想继续使用路线，应在编辑器中清空路线字段或改用普通队伍配置。

### 2.3 配置迁移与用户数据保护

文件：

- `assets/config/config.example.yaml`
- `module/config/config.py` 的 `_merge_builtin_team_presets()`
- `module/config/config_typing.py` 的 `team_presets_revision`

当前默认配置版本为 `team_presets_revision: 4`。加载旧配置时：

1. 读取已保存的 `team_presets_revision`。
2. 只有默认版本更高时才执行一次合并。
3. 以 `remark_name` 判断同名队伍是否已经存在。
4. 同名队伍不覆盖，包含用户自定义修改的队伍也不覆盖。
5. 默认槽位被占用时，寻找下一个可用队伍编号。
6. 保留 `teams_active_queue`，不因为添加预设而启用新队伍。
7. 写入新的迁移版本，避免用户主动删除的内置队伍被每次启动重新加回。

旧配置中的“`小指良伪单通`”不会被重命名或覆盖；新版本只在空闲槽位补充普牢和困牢模板。

这套迁移是“默认配置自动补齐”；队伍页面的预设弹框是“按用户选择写入任意目标槽位”，两者不要混淆。未来增加内置预设时，如果还希望旧用户自动得到该队伍，需要同时更新默认配置和迁移版本；如果只希望用户从弹框选择，则只需要更新目录和 mock 目录。

## 3. 队伍页面、RPC 和保存语义

### 3.1 后端 RPC

文件：

- `module/rpc_dispatcher.py`
- `module/backend_application.py`
- `gpui-app/src/ipc/mock/handlers.rs`

新增/使用的 RPC 是：

```text
team.list          -> 已保存队伍
team.preset.list   -> 只读内置预设目录
team.save          -> 新建或更新队伍
```

`BackendApplication.team_preset_list()` 的处理顺序：

1. 遍历 Python 内置目录。
2. 用相同的 `TeamSetting` 模型校验模板。
3. 调用 `_team_detail(0, setting, False)` 生成完整 `TeamDetail`。
4. 把模板的 `id` 固定为空、`enabled` 固定为 `False`，表示它还不是已保存队伍。
5. 返回 `presetId`、`routeId`、多语言展示字段和完整 `team`。

保存接口的关键约束：

- `id` 为空表示新建；此时可以带 `teamNumber` 指定目标槽位。
- `id` 为 `team-N` 表示更新；更新时不允许再带 `teamNumber`。
- 空槽预设保存后由后端根据 `teamNumber` 生成 `team-N`。
- 已有队伍更新时，后端先深拷贝目标队伍，再写入请求中的完整业务字段。
- `enabled` 缺省时沿用目标队伍的启用状态；经验本队伍强制停用并不进入镜牢队列。
- `mirrorConfig: null` 对已有非经验本队伍不是“清空镜牢设置”，而是保留后端已有镜牢设置；预设保存发送完整 `mirrorConfig`，所以会覆盖路线和镜牢字段。

Rust mock 后端实现同样的 `team.preset.list` 和 `team.save` 语义，便于 GPUI 单元测试和无 Python sidecar 时运行页面。当前 Python 目录和 Rust mock 目录是两份手工同步的数据，增加或修改预设时必须同时检查：

- `module/team_presets.py`
- `gpui-app/src/ipc/mock/handlers.rs` 的 `builtin_team_presets()`

### 3.2 GPUI 状态和操作流

相关文件：

- `gpui-app/src/model/teams.rs`
- `gpui-app/src/state/teams/types.rs`
- `gpui-app/src/state/teams/selection.rs`
- `gpui-app/src/state/teams/persistence.rs`
- `gpui-app/src/app/team_editor.rs`

`TeamPreset` 对应后端返回的完整结构：

```text
presetId
routeId
name
description
floorHint
routeName
team: TeamDetail
```

`TeamMirrorConfig.mirror_route_profile` 使用 `#[serde(default)]`，所以旧 JSON 不带该字段时会得到空字符串并保持兼容。

状态对象中有两个互斥流程：

```text
preset_picker:    当前正在浏览预设，目标可以是空槽或已有队伍
preset_overwrite: 已选择预设、等待已有队伍覆盖确认
```

空槽流程：

1. `list.rs` 的空槽卡片调用 `open_team_preset_picker_for_slot(number)`。
2. `TeamsState` 保存 `TeamPresetTarget::EmptySlot(number)`。
3. 预设卡片点击 `presetId`，`select_preset()` 找到目录项目。
4. 复制预设的完整 `TeamDetail`，清空 `id`，记录 `requested_team_number`。
5. `AhabApp::select_team_preset()` 收到成功结果后立即调用现有 `save_team_editor()`。
6. 保存请求包含完整编队、队伍码、镜牢设置、Gift Search 和路线 ID。
7. 后端按目标槽位保存；保存后刷新队伍列表。

因此空槽选择不会只保存人格列表，也不会因为预设模板的空 `id` 而自动追加到错误槽位。

已有队伍覆盖流程：

1. 已有队伍卡片调用 `open_team_preset_picker_for_team(team)`。
2. 选择预设后不立即保存，而是生成 `TeamPresetOverwriteState`。
3. 覆盖确认框显示目标队伍、目标槽位和预设名称，并明确提示会覆盖全部业务配置。
4. `confirm_preset_overwrite()` 复制预设完整队伍。
5. 只把目标队伍的 `id` 和 `enabled` 写回模板。
6. 进入现有保存流程，更新原记录，不生成新槽位。

取消确认、预设不存在或保存失败时，原队伍不会被替换。覆盖范围包括名称、人格及顺序、队伍码、镜牢配置、Gift Search 和饰品路线；启用/停用状态保留。

### 3.3 两列布局和预设说明

文件：

- `gpui-app/src/pages/teams/list.rs`
- `gpui-app/src/pages/teams/overlay.rs`

队伍列表中的固定槽位和额外队伍都使用 `grid_cols(2)`。空槽固定提供：

- `新建`：调用原有 `open_new_team_for_slot()`，进入原编队编辑弹框。
- `从预设编队选择`：打开预设选择弹框。

已有队伍卡片新增 `从预设覆盖`。预设弹框固定两列，并且每张卡片展示：

- 预设名称；
- 完整说明；
- 适用楼层提示；
- 饰品路线名称；
- 预设人格列表。

选择弹框和覆盖确认框都支持鼠标与键盘激活，点击遮罩或按 `Esc` 会取消当前流程。

## 4. 饰品路线目录

文件：`module/mirror_routes.py`

这是纯数据模块，不依赖 UI、鼠标或 OCR。主要类型如下：

### 4.1 路线类型

`MirrorRouteDefinition` 包含：

- `route_id`、多语言名称和摘要；
- `stages`：对外展示的宽阶段，当前为 1–5、6–10、11–15；
- `gifts`：路线饰品目标；
- `recipes`：路线专用合成配方；
- `floor_counts`：支持的完整镜牢层数，良秀路线为 `(5, 15)`；
- `floor_theme_pack_names`：精确到楼层的主题包别名；
- `skill_replacement_target_counts`：攻略希望的 S1/S2/S3 替换数量。

`GiftRouteTarget` 的字段：

```text
gift_id
names_zh / names_en
start_floor / end_floor
priority        数字越小越优先
protected       是否从破坏性通用操作中保护
asset           可选的专用图片资源
required        路线语义上的必需目标，目前是元数据
```

`GiftFusionRecipe` 的字段：

```text
result_gift_id
result_names_zh / result_names_en
material_gift_ids
start_floor / end_floor
priority
keyword
skip_if_pseudo_solo
```

### 4.2 当前路线内容

`hos_ryoshu_solo_route` 使用以下阶段：

| 逻辑楼层 | 主题包匹配 | 代表性饰品优先方向 |
| --- | --- | --- |
| 1–5 | 无慈悲/信仰与侵蚀、地狱鸡、落花/某个世界、由子弹画下的句点、无改变等 | 霜冻足迹、冻结的哭声、闹鬼的鞋、锋利的针线、探戈腌料、鸡腿、被污染的针线、香料灌木枝、齿轮碎片、暗焰烟斗、默示契约续订、破碎的眼镜、未寄出的信 |
| 6–10 | 1/2 号线、经验记忆、区的奇、时间杀人、教材等 | 马勒、虚假的光环、蛇蜕、礼物系列、紧急调查员徽章、关系的一部分、月之记忆等 |
| 11–15 | 紫色编码、3/5 号线、Chachihu、仲春之夜、教材和安全替代卡包 | 中程 K 公司安瓿、蔑视之眼的蔑视、未孵化的余烬、献给首领、Kkomi 的小礼物、碎裂束缚之炮、觊觎之刺及保命替代饰品 |

源码中的中英文别名是 OCR 输入边界。攻略名称、游戏实际显示名称和中文翻译不一致时，应优先在 `GiftRouteTarget.names_zh/names_en` 增加别名，不要在商店流程中增加新的 `if route_id` 分支。

当前路线配方是：

```text
闹鬼的鞋 + 冻结的哭声
    -> 霜冻足迹

破旧的雨伞 + 破碎的眼镜
    -> 未寄出的信

香料灌木枝 + 破碎的眼镜 + 未寄出的信
    -> 香料灌木、眼镜与寄出的信
```

第三个配方标记 `skip_if_pseudo_solo=True`。因为它依赖多人格效果，进入真正伪单通后不会尝试。

当前有三个 `required=True` 目标：锋利的针线、马勒、中程 K 公司安瓿。它们表达攻略优先级和测试断言，但当前代码不会因为目标没有出现而强制重开或报错；这是“尽量获取”的路线，不是“必得验证器”。

### 4.3 路线解析和兼容别名

```python
get_mirror_route(route_id)
```

解析顺序为：标准 `ROUTES` ID、早期兼容别名、默认路线。未知或空 ID 必须回退默认路线，保证旧配置可运行。

当前目录项为：

```text
hos_ryoshu_solo_route
spiderweb_family_route
""                    # DEFAULT_ROUTE
```

不要用队伍名称或 `preset_id` 判断饰品逻辑；新增预设时新增独立 `route_id`，让一个队伍模板可以更换显示名称，也让未来多个队伍共享同一条路线。

## 5. 路线如何接入镜牢流程

### 5.1 Mirror 初始化

文件：`tasks/mirror/mirror.py`

`Mirror.__init__()` 对传入的 `TeamSetting` 做深拷贝，然后：

1. 如果启用伪单通，先校验人格选择。
2. 用 `team_setting.mirror_route_profile` 得到 `MirrorRouteDefinition`。
3. 用 `route.floor_counts` 创建本轮独立的 `MirrorPlanRuntime`。
4. 用同一份 `TeamSetting` 创建 `Shop`，由 `Shop` 自己解析路线。
5. 保留现有的战斗、队伍码、奖励卡、开局饰品和 Gift Search 逻辑。

这样路线只影响设置了路线 ID 的队伍，不改变默认镜牢队伍。

### 5.2 主题包选择

文件：`tasks/mirror/select_theme_pack.py`

调用形式增加了可选参数：

```python
select_theme_pack(..., route=self.mirror_route)
```

处理方式是“临时叠加权重”：

1. 读取现有中文/英文有效主题包权重。
2. 从 `route.theme_pack_names_for_floor(floor)` 得到当前逻辑楼层别名。
3. 用 `_normalize_theme_name()` 忽略大小写、空格和标点做匹配。
4. 命中的路线主题包权重提升到现有优选阈值以上。
5. 别名靠前的主题包获得更高的路线权重，攻略中的替代项仍可用。
6. `Line 1`、`Line 2` 等数字别名使用边界检查，避免 `Line 1` 错匹配 `Line 10`。
7. 没有命中任何路线主题包时只记录 debug 日志，继续原有刷新和最高权重兜底。

路线权重只修改本次函数读取到的有效权重，不写回用户的主题包权重文件。

### 5.3 奖励饰品和商店购买

文件：

- `tasks/mirror/mirror.py` 的 `acquire_ego_gift()`
- `tasks/mirror/in_shop.py` 的 `Shop.buy_gifts()` 和相关路线匹配方法

奖励饰品出现两个选项时，现有白棉花过滤仍先执行，然后为每个卡片计算：

```text
(是否已持有, 路线优先级或大回退值)
```

未持有的路线目标会优先于没有被路线识别的普通卡；无法识别路线名称时回到原有策略。路线名称通过中文/英文 OCR 匹配，单个饰品可以额外配置专用 asset（目前月之记忆有示例）。

商店购买流程在通用体系购买前，按 `gift_targets_for_floor(current_layer)` 遍历当前楼层目标并尝试购买。路线目标未出现时不阻塞商店，不无限刷新。

### 5.4 饰品保护、路线合成和升级

`Shop` 的破坏性操作包括普通合成、激进合成、出售和通用升级。路线接入方式是公共过滤器，而不是在每个流程里硬编码饰品名称：

```text
_route_gift_id_at_position()
        └─ 当前小区域 OCR / asset / 可选悬浮提示

_route_priority_at_position()
        └─ 得到路线优先级

_remove_route_targets()
        └─ 从通用合成、出售候选中移除路线饰品
```

保护范围有两层：

- `GiftRouteTarget.protected=True` 的路线目标始终保护；
- 后续路线配方的成品和材料也加入保护集合，防止前面拿到的材料在后续楼层前被通用合成或出售消耗。

合成顺序：

1. `fuse_gift()` 首先调用 `fuse_route_gifts()`。
2. 路线配方按当前楼层和优先级排序。
3. 要求能识别成品标签、全部材料标签、现有合成控件。
4. 任意识别条件不满足时取消选择，不点击破坏性确认，让通用流程继续。
5. 已经合成过或库存中已有成品时跳过重复合成。
6. 路线配方结束后才进入激进/普通通用合成；通用流程会继续保护路线目标。

升级时先扫描并按路线优先级升级路线饰品，然后执行本体系四级饰品和旧有通用升级逻辑。

## 6. 5 层 / 15 层运行时判定

### 6.1 为什么不能用固定楼层数

同一个良秀预设可以运行 5 层短流程，也可以运行 15 层困难流程。任务开始时读取 `cfg.hard_mirror`：普通镜牢锁定 5 层，困难镜牢在路线声明支持 15 层时锁定 15 层；只支持 5 层的旧路线仍保持 5 层。`infinite_dungeons` 只表示重复次数，不参与层数判断。

游戏设置页的“未通过楼层”标记只表示当前五层段的进度。首层看到 4 个标记是正常现象，不能再拿它推断总层数。15 层镜牢依赖平行叠加：通关第 5 层和第 10 层后自动确认进入下一段。

### 6.2 `MirrorPlanRuntime` 的职责

文件：`module/mirror_plan_runtime.py`

状态字段：

```text
supported_floor_counts  例如 (5, 15)
floor_count             按任务模式锁定的总层数
current_floor           内部 0-based 楼层
floor_times             每个已开始楼层的时间戳
progress_observed       是否成功观察过进度
deviations              去重后的容错/异常说明
segment_start_floor     当前五层段的内部起始楼层（0、5 或 10）
last_not_passed_floor_count  上一次读取到的当前段剩余标记
```

`detect_floor(not_passed_floor_count, initial=...)` 的规则：

1. 将可见未通过标记数量转成整数，负数或不可转换直接报错。
2. 标记数量属于当前五层段，`4、3、2、1、0` 分别表示该段的第 1–5 层；数量 5 作为首个标记尚未消耗的短暂过渡也映射到该段首层。
3. 只有在确认续层后才把段起始楼层从 0 推进到 5，再从 5 推进到 10；未经确认的标记重置会报错，避免把 OCR 抖动当成进入下一段。
4. 当前楼层由 `segment_start_floor + (4 - remaining)` 计算，内部从 0 开始；路线目录通过 `max(1, floor)` 使用攻略的 1-based 逻辑楼层。
5. 中途恢复任务时，先尝试用 `get_floor_bbox.png` 读取地图标题中的绝对楼层；标题识别区域会保留边缘背景，避免 OCR 把末尾数字丢掉。15 层任务读不到绝对楼层时停止，因为无法确定当前是哪个五层段；5 层任务即使标题读取失败，也会使用当前段的未通过标记计算具体楼层，不会默认第 1 层。

`record_floor_start()` 记录每层主题包选择时间；`complete` 根据锁定的 `floor_count` 判断是否所有楼层都有开始时间，不再写死 5 层完成条件。

### 6.3 镜牢主流程的接入点

`Mirror.get_which_floor()`：

1. 恢复地图时，先读取带 padding 的地图标题区域获取绝对楼层；普通 5 层地图标题读取失败时仍使用首段未通过标记计算具体楼层。
2. 点击镜牢设置页，在固定区域查找 `not_passed_floor.png` 的多个目标。
3. 统计当前五层段标记数量，调用 `plan_runtime.detect_floor()`。
4. 成功后刷新地图楼层并关闭设置页。
5. 失败时记录 deviation、关闭设置页并抛出 `cannotOperateGameError`，交给任务层结束/暂停本轮；不会错误猜测路线。

进入镜牢和续层处理：

- 15 层路线进入前读取“平行叠加模式”；检测为 OFF 时自动点击开启控件并重新确认。
- 无法确认平行叠加已经开启时停止，不会用 5 层逻辑继续执行 15 层饰品路线。
- 5 层结束和 10 层结束的弹窗，15 层模式点击确认并调用 `advance_segment()`；普通模式关闭弹窗。
- `advance_segment()` 成功后将 `get_floor_num` 置回待识别状态，下一段重新读取标记。

主题包页面出现时，主循环将当前路线传入 `select_theme_pack()`，并把楼层开始时间交给 `record_floor_start()`。镜牢结束统计使用 `plan_runtime.complete`，时间统计的最后一层使用 `last_floor_start()`。

现有流程仍负责：

- 5 层结束后的继续/转场界面操作；
- 普通模式拒绝续层、困难模式确认续层；
- `floor_3_exit` 的第 3 层退出语义；
- 重开镜牢和已有奖励领取流程。

路线模块只回答“当前楼层应该优先什么”，不重新实现镜牢转场。

## 7. 小指良动态防御回合

文件：

- `core/pseudo_solo.py`
- `tasks/mirror/mirror.py`
- `tasks/battle/battle.py`

### 7.1 状态包装方式

原有战斗循环只依赖 `remaining_turns` 和 `consume_turn()`。因此没有改写整个战斗循环，而是用 `PseudoSoloDefenseState` 包装原有 `DefenseForSoloState`：

```text
Mirror
  └─ PseudoSoloDefenseState
       ├─ 原有固定回合作为未知识别时的 fallback
       └─ BattleRosterObserver 负责读取队伍页和战斗帧
```

战斗侧仍按原逻辑：剩余回合大于 0 时尝试全员防御，防御成功后消费 1 回合；防御失败则沿用 `P+Enter` 兜底。

### 7.2 队伍页人数计算

在识别到队伍选择页面时，`Mirror` 调用：

```python
self.defense_for_solo_state.observe_team_page(self.floor)
self.shop.set_pseudo_solo_active(self.defense_for_solo_state.live_count == 1)
```

`BattleRosterObserver.read_team_page_live_count()` 的输入优先级：

1. 现有 `teams/{10,11,12}_sinner_live_assets.png` 资产，用于完整队伍常见人数。
2. 较小队伍读取队伍页 OCR 的 `存活/选中` 数字，并校验分母等于选择人数。
3. 无法确认、画面不完整或格式不合法时返回 `None`。

可靠人数 `live_count` 的防御回合为：

```text
max(live_count - 1, 0)
```

也就是排除良秀自己后的其他存活队友数量。例如 12 人为 11 回合，2 人为 1 回合，1 人为 0 回合。

同一楼层、同一人数的重复画面不会重置已经消耗的回合；楼层变化或人数变化会重新同步预算。重开镜牢时 `reset_for_run()` 恢复初始 fallback，并关闭伪单通路线的“仅剩一人”状态。

### 7.3 战斗帧安全确认

队伍页人数是主要依据，战斗帧只负责提前确认“现在已经只剩 1 人”。战斗帧必须连续稳定观察两帧才会把状态切到 `SINGLE_SURVIVOR`；未知或单帧异常不会提前结束防御周期。

人数识别失败时仍使用配置中的 `defense_for_solo_turns`，当前预设为 5。这一字段是安全兼容兜底，不是已知人数情况下的实际回合数。

当 `live_count == 1` 时，`Shop.set_pseudo_solo_active(True)` 会让标记了 `skip_if_pseudo_solo` 的多人格路线配方跳过，避免在伪单通阶段执行不适用配方。

### 技能替换的实际边界

路线目录记录攻略期望的 `skill_replacement_target_counts=(1, 1, 4)`，表示攻略层面的 S1/S2/S3 目标数量。但当前 Python 商店操作接口只能选择全局替换模式，不能精确下发三组独立数量。

因此预设实际使用 `skill_replacement_mode=1` 的当前兼容模式（1→3），运行到技能替换时会记录 warning，明确提示“攻略目标”和“实际兼容执行模式”不同。若以后要完全复刻攻略，需要先扩展商店页面的独立 S1/S2/S3 购买状态和对应资产识别，再把路线目标从日志元数据升级为执行计划。

## 9. 故障排查顺序

### 9.1 预设弹框为空或说明不显示

检查顺序：

1. Python sidecar 是否启动。
2. `team.preset.list` 是否出现在 RPC 方法映射中。
3. `team.preset.list` 返回是否是数组，且每项包含 `presetId`、`team`、`description`、`floorHint`、`routeName`。
4. GPUI `TeamsState::reload()` 是否成功填充 `presets`。
5. 使用 mock 时是否更新了 `gpui-app/src/ipc/mock/handlers.rs`。

界面对应空状态提示是“暂无内置预设 / 请确认后端已完成数据加载”。

### 9.2 选择预设后保存到了错误槽位

空槽请求必须同时满足：

```json
{
  "id": "",
  "teamNumber": 4,
  "name": "小指良伪单通（普牢）",
  "sinners": ["..."],
  "mirrorConfig": {"mirror_route_profile": "hos_ryoshu_solo_route"}
}
```

已有队伍请求必须使用类似 `team-4` 的 `id`，不能再带 `teamNumber`。检查 `TeamEditorState.requested_team_number` 是否只在空槽流程设置。

### 9.3 覆盖没有二次确认或启用状态改变

确认前应存在 `preset_overwrite`，而不是直接存在 `editor`。确认后检查：

- `team.id` 等于目标队伍 ID；
- `team.enabled` 等于目标队伍原状态；
- 其他字段来自预设完整模板；
- 后端更新请求没有 `teamNumber`。

对应测试在 `gpui-app/src/state/teams/mod.rs`。

### 9.4 预设已经保存，但饰品路线没有生效

在 `config.yaml` 检查目标队伍的：

```yaml
mirror_route_profile: hos_ryoshu_solo_route
```

如果为空、拼写错误或仍是旧队伍记录，解析器会回退 `DEFAULT_ROUTE`。路线是在 `Mirror` 创建时读取的，修改队伍后要重新启动该镜牢任务。

接着查看日志：

- `按路线优先购买饰品`
- `按路线优先合成饰品`
- `按路线优先升级路线饰品`
- `保护...当前路线饰品，跳过通用合成/出售`
- `当前楼层未匹配到路线主题包名称，使用现有权重兜底`

如果只出现回退日志，优先检查游戏实际文本是否已加入 `names_zh/names_en`，以及主题包是否已进入 `theme_list`。

### 9.5 主题包选错

重点检查：

1. `route.theme_pack_names_for_floor(floor)` 得到的逻辑楼层是否正确。
2. `Line 1` 是否被错误匹配到 `Line 10`。
3. 游戏当前语言对应的中文/英文有效主题包列表是否包含该名称。
4. 路线权重是否只提升了匹配项，且普通权重没有被写回。
5. 达到刷新上限后是否按最高权重兜底。

日志中的“当前主题包权重列表”可以用来判断是 OCR 未识别、别名不全，还是攻略目标本来没有出现在当前卡包。

### 9.6 路线配方没有合成

依次确认：

- `shop_strategy` 没有关闭合成；
- 没有开启只激进合成或只体系合成模式；
- 当前楼层在配方范围内；
- 成品标签和所有材料能通过 OCR/悬浮提示识别；
- 成品没有已经存在或已经在本轮合成过；
- 当前没有进入 `pseudo_solo_active`，否则多人格配方会主动跳过。

识别不完整时日志通常是“路线配方材料识别不完整，跳过”；这属于保护性回退，不应为了强制合成而去掉材料保护。

### 9.7 5 层/15 层楼层识别或续层被暂停

重点日志：

```text
镜牢路线...任务模式=普通，目标5层
镜牢路线...任务模式=困难，目标15层
困难镜牢目标为15层，但无法自动开启平行叠加模式
困难镜牢平行叠加续层确认未生效，已停止本轮路线
无法读取镜牢剩余层数，已暂停本轮路线
```

排查顺序：

1. 确认任务开始时 `hard_mirror` 是否符合预期：普通目标 5 层，困难目标 15 层。
2. 首层看到 4 个未通过楼层标记是正常现象，它表示当前五层段还剩 4 层，不是总流程剩余 4 层。
3. 困难模式需要在入口自动开启平行叠加；第 5 层和第 10 层出现弹窗时应点击确认，而不是关闭。
4. 若从已有镜牢恢复，确认日志中出现“楼层标题 OCR”并读到 1–15 的绝对楼层；读不到时停止是保护行为。

不要通过修改 `infinite_dungeons` 或硬编码楼层数来绕过，因为重复次数和路线总层数是两个独立概念。

### 9.8 动态防御仍然是固定 5 回合

检查顺序：

1. 目标队伍是否启用了 `defense_for_solo`。
2. 是否真的识别到了 `teams/identify_assets.png` 队伍选择页。
3. `BattleRosterObserver` 是否能识别 10/11/12 人图片，或小队伍的 `live/selected` OCR。
4. `live_count` 是否为 `None`；为 `None` 时使用 5 回合 fallback 是预期行为。
5. 是否在同一楼层、同一人数重复观察；重复观察不会重置预算。
6. 是否发生重开；重开会按设计恢复 fallback，进入下一次队伍页后重新计算。

关键日志：

- `第N层队伍页检测到M名存活己方人格，伪单通连续防御调整为K回合`
- `第N层队伍页确认仅剩1名己方人格，停止连续防御`
- `伪单通检测到只剩一名己方人格，停止连续防御`

## 11. 新增第 N 个预设时的扩展步骤

首版只提供程序内置预设，没有远程 URL 加载。增加新的内置预设时，建议按以下顺序：

1. 在 `module/mirror_routes.py` 增加新的 `MirrorRouteDefinition`，只放数据和别名。
2. 在 `module/team_presets.py` 增加新的 `BuiltinTeamPreset`，分配稳定且不重复的 `preset_id` 和 `route_id`。
3. 在 `gpui-app/src/ipc/mock/handlers.rs` 同步返回同样的 JSON 结构。
4. 如果需要升级旧用户自动出现该队伍，更新 `assets/config/config.example.yaml` 的默认队伍和 `team_presets_revision`；如果不需要，避免无意义地改迁移版本。
5. 为路线阶段、主题包、礼物别名、配方和回退行为补测试。
6. 不修改 `Shop` 和 GPUI 选择逻辑中的公共分支；公共代码应只消费 route/preset 数据。
7. 运行 Python、GPUI 和 upstream boundary 检查。

未来远程 URL 加载应复用当前返回结构，而不是让 UI 认识另一套格式。加载层需要额外负责：

- schema 版本和字段校验；
- `presetId`/`routeId` 唯一性；
- 网络失败时回退内置目录；
- 本地缓存和过期策略；
- 远程内容的签名或可信来源校验。

这些能力目前没有实现，不能把当前内置目录误称为已经支持远程预设。
